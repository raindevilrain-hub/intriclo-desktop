# 나스 Claude Code 세션 슈퍼바이저

나스에서 `claude --remote-control`으로 상시 실행 중인 Claude Code 세션들이 네트워크 순단·
재부팅·프로세스 크래시로 끊겼을 때, 사람이 손대지 않아도 **같은 대화를 이어서** 자동으로
다시 붙게 해주는 Docker 컨테이너.

## 동작 원리 (등록 없이 자동으로 찾는다)

세션 ID를 손으로 등록하지 않는다. 대신 이 컨테이너가 나스의 `~/.claude` 디렉터리를
그대로 들여다본다:

- Claude Code는 세션을 실행할 때마다 `~/.claude/projects/<작업경로의 "/"를 "-"로 바꾼
  이름>/<세션 UUID>.jsonl`에 대화를 저장한다. 이 인코딩 규칙은 이 도구 자신의 세션
  저장소를 직접 열어서 확인한 것이고(추측이 아님), `project_dir`만 알면 그 폴더 이름을
  똑같이 계산해낼 수 있다.
- `claude-sessions.conf`에는 **프로젝트 디렉터리 경로만** 적는다. 슈퍼바이저는 매
  주기마다 그 폴더 안에서 가장 최근에 수정된 `.jsonl`을 찾아 "지금 이 프로젝트의
  진행 중인 대화"로 간주하고, 그게 안 살아있으면 `claude --resume <그 UUID> --bg`로
  백그라운드에서 다시 붙인다.
- 그래서 세션이 어떤 이유로 새 ID를 받아도(예: 4시간 넘게 끊겨서 재연결 기록이
  만료되고 새로 시작된 경우) 다음 주기에 자동으로 그 새 ID를 다시 찾아낸다 — 하드코딩된
  UUID가 없으니 낡을 일도 없다.
- 5분마다 이 확인을 반복한다(`launch-session.sh`는 이미 살아있으면 아무것도 안 하므로
  매번 그냥 다시 불러도 안전하다).
- `docker-compose.yml`의 `restart: unless-stopped`가 가장 바깥쪽 안전망 — 컨테이너
  자체가 죽어도(OOM, 나스 재부팅) Docker가 다시 띄우고, 다시 뜬 컨테이너가 위 과정을
  처음부터 한다.
- 슈퍼바이저는 절대 새 세션을 만들지 않는다. 어떤 프로젝트든 사람이 `claude
  --remote-control`로 최소 한 번은 직접 시작해야 그 다음부터 슈퍼바이저가 이어받는다 —
  그래서 원치 않는 프로젝트에서 멋대로 세션이 생겨날 일이 없다.

## 사무실에서 처음 설치할 때

1. **`.env` 만들기** — `.env.example`을 `.env`로 복사하고 두 값을 채운다:
   - `CLAUDE_HOME`: 지금 실제로 `claude --remote-control` 세션들을 돌리고 있는 계정으로
     나스에 SSH 접속해서 `echo $HOME` 실행한 값.
   - `PROJECTS_ROOT`: 관리할 프로젝트들이 들어있는 공통 상위 경로(예: `/volume1/docker`).
     프로젝트가 여러 상위 경로에 흩어져 있으면 `docker-compose.yml`의 `volumes`에 같은
     패턴으로 줄을 더 추가한다.

   > **왜 컨테이너 안에서 경로를 옮기지 않는가**: Claude Code는 세션이 어느 프로젝트
   > 것인지 실제 작업 경로 문자열 자체로 구분한다. 컨테이너 안에서 그 경로가 달라지면
   > (`/data/projects/...`처럼 다른 경로로 마운트하면) 이미 있는 세션도, 자격증명도
   > 못 찾는다. 그래서 호스트 경로를 그대로, 완전히 같은 경로에 마운트한다.

2. **`claude-sessions.conf` 만들기** — 관리할 프로젝트 디렉터리를 한 줄에 하나씩 적는다.
   직접 타이핑하는 대신, 나스에서 `claude`를 실제로 실행하는 계정으로 한 번 돌리면
   자동으로 채워준다:
   ```
   ./discover-sessions.sh > claude-sessions.conf
   ```
   이미 대화가 있는 모든 프로젝트를 최근 활동 순으로 뽑아준다 — 관리하고 싶지 않은
   줄은 지우면 된다.

3. **`docker compose up -d --build`**로 띄운다.

4. **최초 로그인**: `CLAUDE_HOME`이 맞게 설정됐다면 그 계정의 기존 로그인 정보
   (`~/.claude`)를 그대로 마운트해서 쓰므로 **별도 로그인이 필요 없다**. 컨테이너
   로그(`docker compose logs -f`)에 로그인을 요구하는 메시지가 뜬다면 `CLAUDE_HOME`이
   틀렸다는 뜻 — 1번부터 다시 확인한다. (완전히 새 계정으로 처음부터 시작하는
   경우에만 `docker compose exec claude-supervisor claude login`으로 한 번 대화형
   로그인이 필요하다.)

5. 로그는 `./logs/<프로젝트 이름>.log`(세션별)와 `./logs/supervisor.log`(전체 흐름)에서
   확인.

## 검증 방법 (설치 후 한 번은 직접 해볼 것)

이 슈퍼바이저의 핵심 메커니즘(경로→폴더명 인코딩, `claude agents --json` 스키마,
그걸로 살아있는지 판단하는 jq 필터)은 실제 세션 데이터로 직접 실행해서 검증했다 — 이
저장소를 다루는 이 도구 자신의 `~/.claude/projects`가 바로 그 실증 대상이었다. 다만
**`claude --resume <id> --bg`가 Remote Control 연결 자체까지 되살리는지**는 실제
Remote Control 환경에서 한 번 확인이 필요하다(이 컨테이너를 실제로 로그인시켜 계정에
영향을 주는 테스트라 샌드박스에서는 하지 않았다). 배포 후:

1. 관리 대상 프로젝트 하나를 골라 대화창에서 뭔가 하나 시켜서 최근 대화 이력을 만든다.
2. `docker compose exec claude-supervisor claude agents --json --all`로 그 세션의 pid를
   찾아 `kill`.
3. 5분(또는 `CHECK_INTERVAL`을 짧게 바꿔서 테스트) 안에 `./logs/<프로젝트>.log`에
   재기동 로그가 남는지, 앱(또는 claude.ai/code 세션 목록)에서 그 세션이 다시
   "연결됨"으로 뜨는지 확인.
4. 그 세션 대화창을 열어 2번 이전 대화 이력이 그대로 남아있는지 확인.
5. 문제가 있으면 `launch-session.sh`의 `claude --resume ... --bg` 호출부를 그 결과에
   맞게 조정.

## 알려진 한계 (설계로 없앨 수 없는 것)

- **재연결 유효 시간 ~4시간**: 세션이 끊긴 뒤 4시간을 넘기면 재연결 기록 자체가 만료돼서,
  그 다음엔 대화 이력 없이 새 세션이 시작된다(단, 새 세션도 곧바로 슈퍼바이저 관리
  대상이 된다 — UUID를 하드코딩하지 않으므로). 기본 5분 주기 헬스체크는 이 창을 놓치지
  않기 위한 것이지만, 나스가 4시간 넘게 통째로 다운되면 그 세션들의 이력은 어차피 못
  살린다.
- **레이트리밋**: 관리하는 프로젝트가 많을수록(5시간/7일 창) 한꺼번에 재연결이 몰리면
  걸릴 수 있다. `STAGGER_SECONDS`로 간격을 벌리는 정도로만 완화 가능 — 프로젝트가
  70개가 넘으면 한 바퀴 도는 데만 20~30분이 걸릴 수 있다는 뜻이니, 그보다 짧게
  `CHECK_INTERVAL`을 잡지 않는다.
- **새 프로젝트의 최초 시작은 항상 수동**: 슈퍼바이저는 세션을 새로 만들지 않는다 —
  `claude --remote-control`로 사람이 최소 한 번은 직접 시작해야 한다.
- **완전히 새 계정으로 시작하는 경우의 최초 로그인은 수동**: API 키는 Remote Control에서
  지원하지 않는다. (이미 로그인된 기존 `CLAUDE_HOME`을 마운트하는 일반적인 경우는
  해당 없음 — 위 "최초 로그인" 항목 참고.)
